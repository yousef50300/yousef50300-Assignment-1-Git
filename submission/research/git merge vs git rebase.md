# الفرق بين Git Merge وGit Rebase

بستخدم الاتنين علشان أدخل تغييرات فرع داخل فرع تاني، لكن كل واحد بيرتب تاريخ المشروع بطريقة مختلفة.

## السيناريو

لو عندي فرعان، وكل واحد فيهم عليه تغييرات مختلفة:

```text
          C---D  feature
         /
A---B---E---F    main
```

وعاوز أدخل تحديثات `main` على فرع `feature`.

---

## Git Merge

بدخل على فرع `feature` وبنفذ:

```bash
git switch feature
git merge main
```

`Git` بيحتفظ بتاريخ الفرعين، وبعدها ممكن يعمل `Merge Commit` جديدة تجمعهم:

```text
          C---D-------M  feature
         /           /
A---B---E-----------F   main
```

### اللي بستفيده منه

- بيحافظ على التاريخ الأصلي.
- مش بيغيّر أرقام الـCommits القديمة.
- آمن مع الفروع المشتركة بين الفريق.

### اللي باخد بالي منه

- ممكن يخلي تاريخ المشروع متشعب ومليان `Merge Commits`.

---

## Git Rebase

بدخل على فرع `feature` وبنفذ:

```bash
git switch feature
git rebase main
```

`Git` بياخد الـCommits بتاعت فرعي ويحطها فوق آخر تحديث في `main`:

```text
A---B---E---F---C'---D'  feature
```

أرقام الـCommits بتتغير؛ لأن `Git` أنشأها من جديد فوق نقطة أساس مختلفة.

### اللي بستفيده منه

- بيخلي تاريخ المشروع مستقيم ونظيف.
- بيسهّل قراءة `git log`.
- مناسب لترتيب فرعي الشخصي قبل الـPull Request.

### اللي باخد بالي منه

- بيعيد كتابة التاريخ.
- خطر على الفرع المشترك؛ لأنه بيغيّر أرقام الـCommits.

---

## الفرق زي ما فهمته

| النقطة | Merge | Rebase |
|---|---|---|
| يحافظ على التاريخ الأصلي | نعم | لا |
| يغيّر أرقام الـCommits | لا | نعم |
| قد ينشئ Merge Commit | نعم | لا |
| التاريخ النهائي مستقيم | مش دايمًا | نعم |
| مناسب للفرع المشترك | نعم | لا يُفضل |

---

## حل التعارض في Merge

بعد ما أحل الملفات المتعارضة:

```bash
git add .
git commit
```

ولو عاوز ألغي العملية:

```bash
git merge --abort
```

## حل التعارض في Rebase

بعد ما أحل الملفات المتعارضة:

```bash
git add .
git rebase --continue
```

ولو عاوز ألغي العملية:

```bash
git rebase --abort
```
